## 檔案清單（放到專案對應路徑即可）

```
backend/server/topomap_v2.py          核心資料結構（兩種節點、四種邊、子圖）
backend/build_topomap_v2.py           CLI：讀 output/sessions/<id>/ 生成地圖
backend/tests_fixtures/make_sample_session.py   沒有真實資料時的假資料產生器
backend/server/tests/test_topomap_v2.py         單元測試（54 個，全過）
```

`topomap_v2.py` 完全獨立於現有的 `topomap.py`，不會動到你系統原本的邏輯，
`session.py` / `server.py` 目前都沒有被修改。

## 快速測試（不需要真實導航資料）

```bash
cd backend
python tests_fixtures/make_sample_session.py --out /tmp/demo_session
python build_topomap_v2.py --input /tmp/demo_session --place "測試賣場 demo店"
```

會輸出：
- `output/topomaps/測試賣場_demo店/topomap.png` — 完整版（物件＋所有邊）
- `output/topomaps/測試賣場_demo店/topomap_overview.png` — **總覽版**（只有照片節點
  ＋走道邊，先看這張比較容易看懂整體路線走向）
- `/tmp/demo_session/topomap_v2/` 底下也會各存一份，方便對照這次導航的輸出

再跑一次同一個 `--place`（用新的 session 資料夾）就可以看到它會接在舊地圖後面，
而不是從頭重建。

## 用真實資料測試

你系統現在每次導航會把資料存在 `output/sessions/<session_id>/`，裡面已經有
`photo/`、`annotated/detections_*.json`、`map/map_*.json`，格式跟這支腳本預期的
完全一樣，所以可以直接：

```bash
python build_topomap_v2.py --input output/sessions/<session_id> --place "資工系系辦"
```

## 資料結構對照筆記

| 筆記中的概念 | 對應實作 |
|---|---|
| 第一種節點（拍照位置） | `TopoGraphV2.add_photo_node()`，`ntype="photo"` |
| 第二種節點（辨識到的物件） | `add_object_node()`，`ntype="object"`，含 `role`（商品／標示牌／環境） |
| 子圖 | `get_subgraph(photo_id)` |
| 第一種邊（photo→object，9 種子型態＋距離） | `add_contains_edge()` / `contains_etype()` / `grid_cell_from_box()`，`estimate_distance_m()` 是沒有手機感測器時的暫時公式 |
| 第二種邊（相鄰物件） | `add_adjacent_edge()`，依左到右排序後連相鄰兩兩物件 |
| 第三種邊（跨照片同物件） | `link_same_objects_between_photos()`，貪婪配對（標籤＋OCR招牌＋位置） |
| 第四種邊（走道，單向＝拍照方向） | `add_walkway_edge()`，路徑終點另外呼叫 `set_terminal_facing()` |
| 使用者目前位置 + 移動路徑 | `current_position` / `position_history` / `move_to()` |
| 虛假照片節點（沒走的路） | `add_virtual_branch()` / `resolve_virtual_branch()` |
| 依場所持久化、跨導航更新 | `save_for_place()` / `load_for_place()` |

## 還沒解決 / 只做了局部方案的部分（筆記裡列出的問題）

- **區域呈現**：目前只是在照片節點加一個 `region` 欄位當標籤，不是真正的區域子圖。
- **前後照片沒有共同物體**：`link_same_objects_between_photos()` 配對數是 0 時不會報錯，
  但也沒有補救機制，呼叫端要自己注意。
- **貨架物體被視為整體**：這個要等你們實際用 GroundingDINO 跑過賣場資料才能評估，
  目前的物件節點結構本身沒有限制，但關聯/角色判斷的準確度會受影響。
- **使用者走出已建地圖範圍**：`move_to()` 目前預設要求兩個照片節點間必須已經有
  走道邊才能移動（`require_walkway=True`），走出範圍時會丟出例外，還沒設計自動處理方式。

物件關聯（第三種邊）跟角色判斷都是先用「標籤/OCR文字比對」的規則式做法，
沒有像 ConceptGraphs 那樣用 CLIP 語意相似度，因為目前系統的偵測結果本來就沒有
視覺特徵向量。如果之後想比照論文做法，可以在 `link_same_objects_between_photos()`
裡加一個可選的 embedding 相似度分數。

物件相鄰關係文字（第二種邊）目前是模板產生（`"{A} 在 {B} 的左側"`），
`build_subgraph_from_detections()` 有留 `relation_fn` 參數，可以接你們的
`llm_gateway.py` 讓 LLM 生成更自然的描述，先沒串是因為想讓這支腳本能完全離線跑。

## 這次改了什麼（2026/07/19，根據你上傳的 8 節點真實資料調整）

**1. 地圖太亂 → 換掉版面配置**

原本用 `nx.spring_layout()`，節點位置是演算法自己「彈簧模擬」出來的，
節點一多就會擠成一團互相纏繞。改成沿著走道邊排成一直線的「主幹＋吊掛物件」
版面：照片節點照實際走的順序排一排，物件節點吊在自己照片節點下方，
一眼就能看出使用者實際走的路線。另外新增 `render_png(mode="backbone")`，
只畫照片節點跟走道邊，需要先看整體路線走向時可以先看這張。

**2. 跨照片同物件關聯過度連結 → 收緊判斷門檻**

你上傳的真實資料裡，8 張照片、74 個物件卻連出 72 條「同物件」邊，
仔細看內容發現大多是 `trash↔trash`、`desk↔desk`、`plant↔plant` 這種
被誤判的配對。原因是實際系統輸出的 `detections_*.json` 幾乎都沒有
`position` 欄位，導致我原本設計的評分公式退化成「標籤字串一樣就算配對」
——而辦公室走廊裡本來就到處都是垃圾桶、桌子、盆栽，光看標籤完全無法
區分是不是同一個。這次改成：
  - 沒有 `position` 欄位時，改用偵測框座標自己算一個畫面位置（左右／上下），
    不再依賴那個常常是空的欄位；
  - 配對門檻從 1.0 分提高到 1.6 分，代表「只有標籤一樣」不足以判定為同一物件，
    至少要多一項空間位置或招牌文字佐證；
  - 預設不對「門、牆、窗」這類環境／結構物件做跨照片關聯（`allow_structural=True`
    可以覆蓋），因為這類物件每張照片幾乎都會出現，用標籤配對幾乎一定會誤判。

## 這次又改了什麼（同一天，第二輪：配色、節點文字、目前位置標示）

- **節點改成「依文字內容自動算多大」的方塊**，不再是固定大小的圓點/方塊。
  文字絕對不會被截斷、也不會突出節點邊界；連 `cabinet bookshelf shelf` 這種
  很長的組合標籤都能完整顯示在自己的框裡。
- **節點間距也改成依方塊實際大小計算**，不再用固定間距，所以不會互相重疊
  （包括物件群跟隔壁照片的物件群）。
- **換了一組更柔和的配色**：照片節點深藍綠 `#264653`，物件節點暖金色
  `#E9C46A`，走道邊珊瑚橘、相鄰邊青綠、跨照片同物件邊紫色，比原本飽和的
  藍/橘更耐看。
- **圖例改成畫布最上方的獨立橫條**，不再疊在圖的左上角蓋住節點（圖比較小
  的時候原本會蓋到）。
- **「使用者目前位置」從蓋住整個節點的巨大紅色星星，改成畫在該照片節點
  右上角的一顆小紅星徽章**——見下方說明。

### 那顆紅色大星星是什麼意思？

代表**使用者目前所在的照片節點**（也就是 `current_position`，導航到目前
為止最後拍到的那個位置）。舊版是畫在節點正中央、蓋住文字的巨大星星；
新版改成畫在那個節點方塊右上角的小星星徽章，一樣代表「這裡是目前位置」，
但不會擋住節點本身的標籤。

## 這次改了什麼（第三輪：死算推位版面，貼近實際場景分布）

之前的版面是把所有照片節點強制排成一條直線（不管實際路線有沒有轉彎），
物件群固定吊掛在正下方。這次改成：

- **以第一張照片（id 最小）當原點 `(0, 0)`**，之後每個節點的位置都是從
  這裡沿走道邊「走」出來的——符合你說的「先把第一張照片定為原點」。
- **沿走道邊的方向文字做死算推位**：解析每條走道邊 `direction` 欄位裡的
  文字（這是 VLM 生成的自然語言，例如「請直走，然後再拍一張照片」「請
  右轉」），抓「左轉／右轉／迴轉」等關鍵字轉換成角度，抓得到「幾公尺」
  的數字就用來抓步伐長度，抓不到就用一個固定的預設步長代替。這樣路線
  轉彎的地方，地圖上也會跟著轉，不再是死板的一直線。
- **物件群吊掛的方向會跟著走道朝向旋轉**：不再永遠掛在正下方，而是掛在
  該節點所在那段走道的側邊，路線轉彎時，物件群的方向也會跟著轉，比較
  像貼著實際走道排列。
- **虛假分支節點（沒走過的路）也會依方向文字偏到正確的側邊**（例如
  「往右側走道」就會偏到主線的右側，不是疊在主線正上方）。
- 節點間距、防止文字重疊的邏輯不變，只是現在整體形狀是 2D 的，不是一維的。

**這仍然只是「大概的形狀」，不是量出來的真座標**——沒有羅盤/步伐感測器，
角度只能抓文字裡的關鍵字（例如「先直走再右轉」這種同一句話裡出現多個
動作的複雜語句可能抓不準），距離抓不到數字時也只能用固定步長代替。等
之後手機端真的送方向/距離感測器資料進來，可以把這裡的關鍵字解析換成
真正的感測器數值，形狀會更準確。

你上傳的這份真實資料裡，VLM 產生的方向文字全部都是「請直走／請繼續直走」
（沒有出現轉彎），所以死算推位算出來的形狀本來就會是一直線——這其實是
正確反映了這次真實路線本身就是一路直走。已經另外用合成測試資料驗證過
轉彎（直走→右轉→直走→左轉）會正確畫出轉折的形狀，附件裡也有這張測試圖。




## 這次改了什麼（第四輪：修掉節點互相覆蓋、放大文字）

你上傳的最新測試結果裡，物件節點會一整排疊在一起（例如
`cabinet bookshelf shelf` 疊在 `desktop computer water dispenser` 上面）。
原因找到了：物件群分成好幾「列」吊掛在照片節點側邊時，列與列之間的間距
原本用一個固定值（不管方塊多寬多高），但這次的路線（在你的真實資料裡）
剛好是正南北走向，導致「列跟列之間該留多少距離」跟「方塊本身的寬度」
變成同一個方向——方塊本身動辄 3~4 個資料座標單位寬，固定間距完全不夠，
所以整排疊在一起。

修法：現在會先算「方塊的寬/高投影到列間距方向後各佔多少空間」（矩形投影
到任意方向的公式：`|寬 × 該方向的水平分量| + |高 × 該方向的垂直分量|`），
再用這個真正需要的空間來決定列與列的間距，不管走道朝向是水平、垂直、還是
斜的，物件方塊都不會疊到彼此。

另外把照片節點跟物件節點的文字都調大了（照片節點 11pt → 13.5pt，
物件節點 9pt → 11pt），方塊大小是「先量文字多大再決定」，所以字變大、
方塊也會跟著變大，不會被截斷。

新增一個回歸測試 `test_object_rows_do_not_overlap_when_corridor_is_axis_aligned`，
用一堆長標籤 + 走道方向固定為正南北向（最容易踩到這個 bug 的情境）驗證
所有物件方塊兩兩之間都不重疊。

## 這次改了什麼（第五輪：修正「請轉身」沒被辨識成迴轉的 bug）

分析你這次上傳的真實 17 節點資料時發現：路線中段有「請向右轉」（有正確
辨識成右轉）跟兩次連續的「請轉身，然後沿著走廊返回」——但「轉身」這個
詞不在我原本的迴轉關鍵字清單裡（原本只有「迴轉」「掉頭」「回頭」），
導致這兩次迴轉被當成「沒有轉彎」處理，路線本來應該要折返，卻被畫成
繼續往同一個方向直走，跟真實走法對不起來。

修法：把迴轉關鍵字擴充成「迴轉、回轉、掉頭、回頭、轉身、折返、往回走、
退回」，涵蓋更多常見的翻譯講法。用你的真實資料重新驗證過：兩次連續的
「轉身」現在會正確疊加成 360 度（等於繞回原本方向），路線形狀也確實出現
折返效果，不再是一路直走的假象。

另外把節點文字原本設定的「粗體」拿掉了——這是造成你截圖裡那些
`findfont: Failed to find font weight...` 警告的原因（你的機器上找到的
中文字型檔案，matplotlib 沒辦法正確抓到粗體版本，抓不到就退回很細的字重，
警告訊息不影響地圖產生，但看起來很吵）。文字現在維持一般字重，配合已經
放大的字級，還是清楚易讀。

新增 2 個測試：`test_parse_turn_degrees_recognizes_turn_around_phrasing`
（驗證「請轉身」「請往回走」「請掉頭」都能正確辨識成迴轉）、
`test_double_turn_around_cancels_out_like_real_session_data`（直接對應
你這份真實資料連續兩次迴轉的情境，驗證角度真的有疊加抵銷回原方向）。

## 這次改了什麼（第六輪：同物件關聯邊變兩條弧線、P0/P8/P15 是什麼意思）

**Q: 判定為同物件的兩個物件節點之間，為什麼畫出來是兩條弧線？**

因為第三種邊（跨照片同物件）在資料裡是「雙向各存一條」（`A→B` 跟
`B→A` 各一條，方便沿著任一方向查詢鄰居），這是設計上故意的，不是錯誤。
但畫圖時如果把這兩條方向相反的邊都畫出來，因為用的是有弧度的線
（`connectionstyle="arc3"`），方向相反時弧會往兩邊彎，疊在一起就變成
你截圖裡看到的「兩條弧線像一對眼睛」。

**這是純粹的畫圖問題，資料本身沒有錯**——但既然會造成誤解，還是修掉了：
畫圖前先把每一種雙向邊（相鄰物件、跨照片同物件、走道）都依「無序的節點
對」去重，同一對節點只畫一條線／一條弧。用你的真實資料重新產生過，
原本的雙弧線現在只剩一條。

**Q: 照片節點的 P0、P8、P15 是什麼意思？**

具體來說：一個物件就算整個都在路徑的側邊、根本沒有擋到任何東西，
只要它沿著邊方向的投影距離剛好比較遠，就會被算進縮排——縮排因此被

這條邊的路徑上」（物件方塊到這條線的垂直距離，小於等於物件方塊在
垂直方向上的半寬）時，才會被算進縮排；物件不管沿邊方向的投影距離
多遠，只要整個方塊都在線的側邊、沒有真的擋到路徑，就不會影響縮排。
縮排至少會保留照片節點自己方塊的份（一定要清掉自己），只有真的有

## 這次改了什麼（第十九輪：修正第十八輪造成的九宮格上下顛倒）

你回報九宮格的排序方式上下顛倒了。查了一下，這是第十八輪的副作用：

第十八輪把物件的堆疊方向從「背對拍攝方向」（`-row_axis`）改成「順著
拍攝方向」（`+row_axis`），但只改了堆疊延伸的方向，**忘記把「同一欄
內由近到遠」的排序也跟著反過來**。原本（背對方向時）的排序是「上排

方向一起調整，直接套用到新的延伸方向上——結果變成：上排的物件反而
落在堆疊「靠近照片節點」的那一端，下排的物件落在「疊最遠」的那一端。
因為堆疊統一只往一個方向延伸，「離照片節點的遠近」自動對應到畫面上
的某個方向，順序沒跟著方向一起翻過來，畫出來的上下關係自然就顛倒了
——上排看起來在下面，下排看起來在上面。

修法很直接：把同一欄內的排序**反過來**，改成「下排（row=2）最先排、
離照片節點最近，上排（row=0）排最後、疊最遠」。這樣堆疊往同一個方向
延伸出去之後，上排物件會落在離照片節點最遠的那一端，下排落在最近的
那一端，跟畫面上「離照片節點越遠＝原照片裡越上面」的方向一致，九宮格
的上下關係才會跟原照片相符，不再顛倒。

九宮格的「欄」（左/中/右）排序完全沒受影響，只有「列」（上/中/下）
對應到的堆疊順序反過來。既有的 `test_object_layout_follows_grid_cell_row_order`
測試更新了斷言方向（上排的 depth_dist 現在應該最大，不是最小），語意
說明也一併更新。用你的真實資料重新驗證：節點兩兩重疊維持 0 對，圖
照常畫得出來。單元測試維持 47 個，全過。

## 這次改了什麼（第二十一輪：間距改用方向性估計、修正連帶發現的震盪 bug）

### P16→P17 間距特別長的原因

你指出有些照片節點間距還是偏長，P16、P17 之間最明顯。查了一下：
P16→P17 這條邊死算推位算出來的原始距離只有 3.2（跟其他邊差不多），
但最後畫出來變成 11.32——因為 P17 自己剛好有 6 個物件（sofa、desk、
computer、chair、filing cabinet、trophies）疊在同一欄，物件群的
「可能延伸範圍」（`cluster_reach`）因此很大。問題是：原本 `min_dist`
的安全間距計算不分方向，兩端（P16 跟 P17）都套用「物件群可能伸多遠」
這個保守估計——但 P17 那些物件是往 P17 自己的拍攝方向延伸（第十八輪
定的規則：物件在鏡頭前方），也就是遠離 P16 的方向，根本不會佔用
P16、P17 之間的空間，用不分方向的估計去抓間距是不必要的浪費。

修法：`min_dist` 改成優先用方向性的估計——**只有這條邊「沒有轉彎」**
（父節點、子節點的拍攝方向相同）時套用：父節點的貢獻用它自己物件群
「往子節點方向」實際伸展多遠（`cluster_forward_reach`，這個方向的
估計是準的，因為父節點的物件群本來就是往這個方向堆疊）；子節點的
貢獻只用它自己照片方塊的半寬（`photo_row_axis_extent`）——子節點的
物件是往「遠離父節點」的方向延伸，不會佔用父子之間的空間。有轉彎的
邊沒辦法這樣簡化（父節點的物件群延伸方向跟這條邊的方向不一致），
維持原本不分方向的保守估計。

用真實資料驗證：**P16→P17 從 11.32 降到 3.81**，整體路徑長度從
第二十輪的 60.98 附近（第二十輪縮小倍率後的結果）左右微調到差不多
的水準（這次主要是修正個別偏長的邊，不是整體再大幅縮短），節點兩兩
重疊維持 0。

### 順便修正的震盪 bug

改動間距公式、排版變得更緊湊之後，測試時發現一個原本就存在、但要
夠緊湊才會被觸發的 bug：`_resolve_cluster_overlaps`（防止群跟群整塊
重疊）跟 `_resolve_edge_node_crossings`（防止走道邊被無關節點擋住）
兩個機制在某些情況下會互相拉扯，一個把節點群拉回來、剛好又把它推回
另一個機制想避開的路徑上，來回震盪永遠收斂不了。

修法有三個部分：
1. 交替修正的迴圈次數從 6 輪加到 30 輪，給更多機會收斂。
2. 加入循環偵測——如果同一組座標（四捨五入後）重複出現，代表卡進
   循環了，之後的走道邊穿越修正改用逐步加大的推擠幅度，試著跳出。
3. 修正 `_resolve_edge_node_crossings` 本身的兩個精確度問題：
   （a）推擠量原本用 `max(寬,高)/2` 估計，方塊被邊斜著切過去時這個
   估計可能不夠，改成用投影到「垂直於這條邊」方向的正確半寬公式；
   （b）同一個群如果有好幾個物件（同一欄堆疊很深）先後擋在路徑上，
   原本是逐一物件各推一點點，容易變成「推開這個、換下一個卡上去」，
   改成一次用「整個群所有成員」裡最寬的估計去算清空距離，一次推到位，
   不會每輪都在跟另一個機制拉扯不同的物件。

用你的真實資料重新驗證：節點兩兩重疊、走道邊完整線段被無關節點擋住
的情況都維持 0。單元測試現在總共 49 個，全過。

## 這次改了什麼（第二十二輪：全面驗證角度、改善角度復原的成功率）

### 驗證方法

你要求全面確認每個照片節點的角度正確性。我寫了一個驗證腳本，對每一段
相鄰照片節點（P1→P2、P2→P3……P16→P17）做三方比對：
1. **資料本身**：這段路的方向文字（例如「請繼續直走」「請向右轉」）
   解析出來的轉彎角度。
2. **死算推位**：`_dead_reckon_tree()` 照這個轉彎角度累加算出來的
   原始方向（這是「理論上完全正確」的角度，還沒套用任何防重疊調整）。
3. **最終渲染**：`_layout_positions()` 跑完所有排版步驟（含防重疊、
   角度復原）後，這兩個照片節點實際畫出來的方向。

理論上第 2、3 項應該完全一致（角度復原機制的目的就是確保這件事）。

### 驗證結果

用你這份資料（17 張照片、16 段路），**14 段完全一致**，**2 段有落差**：

| 路段 | 資料角度 | 修正前渲染角度 | 落差 |
|---|---|---|---|
| P10→P11 | 90.00° | 81.21° | 8.79° |
| P11→P12 | 270.00°（即 -90°，對應「轉身」180 度轉彎後的方向） | 298.14° | 28.14° |

兩段都在折返路段（P11→P12→P13 是連續兩次「轉身返回」，本來就是全圖
最擁擠的區域）。追查後確認根因：角度復原機制（第二十輪加的）原本是
「要嘛完全修正到位，要嘛完全不修」——這兩段剛好都是「完全修正會重新
造成重疊或穿越」的情況，所以整段被放棄，維持防重疊推擠後的角度，
偏差就這樣留下來了。

### 修法：漸進式角度修正

把「全有全無」改成漸進式：先試 100% 修正（完全對齊死算推位的角度），
不安全的話依序試 75%、50%、25%（相當於朝正確角度轉一部分，不是轉到
底），取「能安全套用的最大幅度」。這樣即使沒辦法完全修正，也能盡量
修正到接近正確的角度，比「完全放棄」更接近真實資料。

用你的真實資料重新驗證：

| 路段 | 資料角度 | 修正後渲染角度 | 落差 |
|---|---|---|---|
| P10→P11 | 90.00° | 87.81° | **2.19°**（原本 8.79°，改善 75%） |
| P11→P12 | 270.00° | 298.14° | 28.14°（無法改善，見下） |

P11→P12 這段實際追查發現：連 25% 幅度的修正都會重新造成走道邊穿越
（`_has_crossing()` 仍然是 True），已經試過所有預設的漸進幅度都不安全
——這不是 bug，是這個折返點本身空間真的很緊（P11、P12、P13 三個節點
因為連續兩次 180 度轉身，彼此距離很近），要嘛接受這段角度有偏差，
要嘛得犧牲「不能重疊/穿越」這個更優先的要求，兩者只能選一個，目前
維持「不重疊優先」的既有原則。

節點兩兩重疊維持 0 對（漸進式修正沒有引入新的重疊風險，因為每個
幅度套用後都會重新檢查）。單元測試維持 49 個，全過（既有的角度復原
測試在漸進機制下依然通過，因為那個測試場景本來就允許 100% 完全修正）。

### 給你的建議

如果 P11→P12 這 28 度的角度偏差在意的話，有兩個方向可以再往下處理，
但都需要你確認要不要做：
1. **放寬折返區域的間距**：目前這三個節點（P11/P12/P13）的間距是
   死算推位的預設步長（沒有明確公尺數時的固定值），如果實際導航資料
   有拍到更精確的距離，或願意手動加大這個折返區域的最小間距，空間
   寬裕一點，角度復原就有機會成功。
2. **接受現狀**：這個偏差只出現在這一個特別緊的折返點，其餘 14 段
   都完全正確，且不重疊、不穿越的保證沒有被犧牲，作為一個獨立的
   視覺化工具，這個程度的取捨目前看來是合理的。

## 這次改了什麼（第二十三輪：找不到路徑的節點，排版擺到版面外）

`locate_v2.py`（照片定位功能）需要把一張查詢照片畫成地圖上的**獨立
節點**，刻意不接任何走道邊（見 `README_locate_v2.md`）——這種節點在
`_dead_reckon_tree()` 眼中「找不到路徑連過去」，原本的後備邏輯只是
貼著起點（root）挪一點點小偏移量：

```python
xy[n] = (ax_ + (i + 1) * self._DEFAULT_STEP_UNITS, ay_)
```

問題是起點旁邊本來就有自己的物件群展開，這個小偏移量完全不夠，會直接
疊到主路徑的節點/物件上，嚴重影響可讀性——這不是 `locate_v2.py` 自己
能修的（它只負責建圖副本、呼叫既有的 `render_png()`），問題出在
`_dead_reckon_tree()` 這段後備邏輯本身。

**修法**：算出目前所有已排版節點座標的邊界框，把這種「找不到路徑的
節點」排在邊界框下方留一大段安全間距的地方，橫向排開一列（多個的話
彼此也留夠物件群可能展開的空間），保證落在先前完全沒有東西的空白
區域，不會疊到主路徑或任何物件群上。

用真實地圖資料驗證：查詢節點確實被排到地圖下方大片空白處，不再跟
P1～P17 的任何節點/物件重疊。新增測試
`test_leftover_node_without_walkway_is_placed_outside_main_map_bounds`，
建一條有物件群的主鏈，加一個完全沒有走道邊連接的獨立節點，驗證排版後
它的方塊跟其餘所有節點的邊界框完全沒有重疊。

## 這次改了什麼（第二十四輪：OCR 資料一直沒有真正關聯到物件上）

`build_subgraph_from_detections()` 有一個 `ocr_items` 參數，原本設計
的用意是「把這批 OCR 結果拿去跟物件做關聯」，但函式內部從頭到尾根本
沒有寫任何程式碼去真的使用這個參數——它被接收進來，然後就晾在那裡。
物件要有 OCR 文字，原本的邏輯只認「這個物件的字典裡，自己本來就帶著
`nameplate_text` 這個欄位」；但系統實際存的偵測結果，OCR 常常是**獨立
分開存的一份清單**（`detections_*.json` 裡的 `"ocr": [...]`），不是
寫在每個物件自己身上——這兩者從來沒有被串起來過。

這是一個從系統一開始就存在、沒被發現過的既有漏洞（`build_topomap_v2.py`
跟 `locate_v2.py` 都共用這個函式，兩邊都受影響），是在排查「照片定位
功能信心分數異常低」時，順著追查才挖出來的。

**修法**：新增 `_associate_ocr_with_detections()`，在
`build_subgraph_from_detections()` 一開始，把 `ocr_items` 清單裡每一筆
OCR 結果，依座標關聯到**距離最近的物件**，寫進該物件的 `nameplate_text`
欄位（相容四點多邊形、簡單矩形兩種常見的 bbox 格式）。有兩個細節：

- **物件本身已經有 `nameplate_text`／`ocr_text` 的話不會被覆蓋**（例如
  某些 VLM 輸出格式本來就會直接把文字寫在物件自己身上）。
- **距離打平手時（VLM 模式常見：好幾個不同物件共用同一個粗略模板框，
  中心點完全一樣），優先選標籤本身比較像招牌／告示牌的物件**（`sign`、
  `board`、`notice` 等關鍵字），不是隨便選排最前面那個——同樣是打平手，
  一段文字關聯到「sign」會比關聯到「door」更合理。

這個修正也連帶影響角色判斷：`classify_role()` 本來就會優先看「有沒有
OCR 文字」，一旦某個物件（例如貼著房間牌子的門）透過這次修正拿到了
`nameplate_text`，會直接被歸類成「標示牌」，不再是「環境結構物」——
這代表這類物件現在會自動有資格參與物件比對／關聯，不需要額外的規則。

**這個修正只影響「以後建圖/定位時」的行為，不會回頭修改已經建好的
地圖資料**——現有地圖需要用修正後的 `topomap_v2.py` 重新跑一次
`build_topomap_v2.py`（加 `--fresh`），OCR 資料才會真的補上去。

新增 4 個測試：`test_ocr_items_are_associated_to_nearest_object_by_position`
（基本關聯邏輯）、`test_structural_object_with_associated_ocr_is_classified_as_sign_not_structure`
（驗證帶 OCR 文字的門會被歸類成標示牌）、
`test_ocr_association_does_not_overwrite_existing_nameplate_text`
（已有文字不被覆蓋）、`test_ocr_association_ties_prefer_sign_like_labels`
（VLM 模式模板框共用座標打平手時，優先關聯給招牌類標籤）。

單元測試現在總共 **54 個**，全過。
