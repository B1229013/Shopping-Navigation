# 照片定位（locate_v2）— 使用說明

跟 `topomap_v2.py` / `build_topomap_v2.py` 配套的測試工具，回答的問題是：
**「給一張新照片，能不能在既有的拓樸地圖裡推理出它可能位於哪個位置？」**

跟 `build_topomap_v2.py` 一樣先做成「不跟系統整合」的獨立離線工具。

## 檔案清單

```
backend/server/locate_v2.py                核心比對邏輯（localize_photo() /
                                             render_localization_debug_png()）
backend/locate_photo_v2.py                  CLI（支援 --detect-mode vlm/
                                             groundingdino/auto、--detect-runs
                                             多輪偵測合併）
backend/diagnose_detection_mode.py          診斷工具：掃描 session 資料夾，
                                             判斷每張照片當初是用哪種偵測模式
                                             建的（見下方「偵測模式」說明）
backend/server/topomap_v2.py                建圖核心（這次順帶修過：OCR 關聯
                                             到物件、找不到路徑的節點排版）
backend/server/config.py                    LABEL_SYNONYMS 同義詞表（這次
                                             擴充了辦公室/室內家具類別）
backend/server/tests/test_locate_v2.py      單元測試（31 個，全過；含用真實
                                             92 節點地圖資料做的整合測試）
backend/server/tests/fixtures/real_place_topomap.json
                                             上面整合測試用的真實地圖 fixture
```

## 比對邏輯（完整版，五層）

不是「標籤相同就算數」這種單純規則，由下而上分五層：

**第 0 層／標籤正規化**：GroundingDINO/VLM 對同一個實體，不同次可能標成
不同字串（`sofa` vs `couch`）。先查 `config.LABEL_SYNONYMS` 同義詞表收斂
成標準詞（取最長變體優先，避免 "cabinet shelf" 被籠統的 "shelf" 誤判），
再依「有沒有 OCR 文字」分類角色（有文字 → 標示牌；門/牆/窗等 → 環境
結構物；其餘 → 商品）。

**第一層／單一配對分數**：
```
配對分數 = 標籤相同 × 稀有度權重(0.15~1.0，這個標籤在地圖裡越少見權重越高)
         + OCR/招牌文字相同 × 1.2
         + 垂直位置加分（只在標籤或OCR已對上時才生效）：
             完全同格 +0.15、差一格 +0.07、差兩格 +0
```
只比垂直（上/中/下），不比水平（左/中/右）——水平會隨拍攝站位、朝向
改變甚至鏡像顛倒，不可靠。分數 <0.05 的組合直接捨棄。環境結構物（門/
牆/窗）預設不參與比對，但**帶 OCR 文字的結構物破例放行**（一扇貼著
房間牌子的門很有鑑別力，不該被排除）。

**第二層／貪婪配對**：所有候選配對依分數高到低排序，分數高的優先
「訂下來」，物件一旦被用過就不能再配對第二次。

**第三層／雙向覆蓋率**：
```
Rn = 配對分數總和 / (節點所有物件的稀有度權重總和 + 1.2)
Rq = 配對分數總和 / (查詢照片所有物件的稀有度權重總和 + 1.2)
覆蓋率 = 2·Rn·Rq / (Rn+Rq)   ← 調和平均，任一邊證據不夠就被拉低
```

**第四層／空間排列一致性**：對所有配對成功的物件兩兩一組，檢查「誰在
誰上面」在兩張照片裡是否一致，算出一個乘數：
```
配對數 ≥2、能比較出順序 → 依一致比例算（貝氏平滑）
配對數 <2（證據太少）    → 固定 0.5
配對數 ≥2 但都同一垂直格（非證據不足，是沒有差異可比）→ 固定 0.85
```

```
最終分數 = 覆蓋率 × 空間排列一致性乘數
```

**不會修改傳入的地圖**（內部對整份地圖 `deepcopy` 之後才動作）。全程
沒有呼叫任何 AI 模型，純規則式運算；模型只用在更早的「照片→偵測結果」
這一步。完整公式、每個常數的取值理由，見 `server/locate_v2.py` 檔頭。

## 偵測模式：GroundingDINO 或兩階段 VLM

系統依 GroundingDINO 有沒有成功載入，自動切換兩套偵測邏輯：

- **模式 A（GroundingDINO）**：逐一精確框選候選詞清單裡的物件
- **模式 B/C（兩階段 VLM）**：改用 LLM 直接用文字描述整個畫面，物件
  位置是「粗略九宮格＋近遠」文字描述，`box` 座標是依這段文字換算出來
  的固定模板，不是逐一量測的結果（VLM 沒辦法可靠輸出精確座標，這是
  刻意的設計取捨，不是資料有問題）

實測發現：拿模式 A 重新偵測、去跟模式 B/C 建出來的地圖節點比對，即使
畫面內容一樣，物件標籤的用詞、精細度也會差很多——不是同一套方法產生
的東西，比不起來，不是環境設定或版本問題。**目前系統實際建圖已統一
改用模式 B/C（VLM），`locate_photo_v2.py` 的 `--detect-mode` 預設也
跟著改成 `vlm`**：

```bash
python diagnose_detection_mode.py --session-dir output/sessions/<id>
```

這支診斷工具可以掃過整個 session，統計每張照片實際是哪個模式建的
（判斷依據：偵測結果裡有沒有 VLM 後處理專屬欄位、有沒有 2 個以上不同
標籤共用完全相同的座標）。

## 多輪偵測合併（`--detect-runs`）：降低 VLM 模式的信心分數波動

實測發現：同一張照片、同一支程式，VLM 模式連續跑三次，分別偵測到
5、7、7 個物件，其中一次漏讀了門上的 OCR 文字，導致最終信心分數在
55%~75% 之間跳動——核心物件（desk/chair/sofa 這種明顯的東西）三次都
配對到同一批，純粹是「這次有沒有順手多注意到一兩樣東西、有沒有讀到
某段文字」每次有出入。這是 VLM（語言模型）本身的特性，不是 bug——
GroundingDINO 模式已經驗證過「同一張圖連續跑兩次，結果位元級相同」，
只有 VLM 模式才有這個問題。

`--detect-runs N`（N>1）讓 CLI 真的把偵測重複跑 N 次（各自獨立呼叫
模型，花 N 倍時間／API 額度），再合併成一份查詢物件清單。合併規則
（`_merge_multi_run_detections()`）：對每個標籤，分別統計它在「每一輪
各自」出現幾次，取**單一輪次裡出現次數最多**的那一組當代表——不是把
各輪次的數量加起來（那樣會把「同一個實體因為每輪判斷位置有些微落差
而被誤拆分」的雜訊也一起加總，物件數只會越合併越膨脹，我們踩過這個
坑，見下方問題修正表格）。只出現在部分輪次的標籤一樣會被保留（聯集，
不是交集），OCR 文字用「同標籤、數量一樣」的其他輪次依順位回填。

**實測效果**（同一張從 P17 位置、但角度略有不同拍攝的照片，各測 3 次）：

| | 分數範圍 | 波動幅度 |
|---|---|---|
| 單次（`--detect-runs 1`） | 55.1% ~ 74.7% | 19.6 個百分點 |
| 兩輪合併（`--detect-runs 2`） | 67.2% ~ 71.1% | **3.9 個百分點**（縮小約 80%） |
| 三輪合併（`--detect-runs 3`） | 57.8% ~ 71.1% | 13.3 個百分點（一次離群值：3 輪剛好都漏看同一樣東西，機率上偶爾會發生，不是邏輯錯誤） |

**兩輪合併（`--detect-runs 2`）目前實測下來報酬率最高**——用兩倍成本
換到波動大幅縮小的效果，三輪合併理論上該更穩定，但目前這批測試沒有
展現出比兩輪更好的效果（多測幾次應該會回到平均值附近）。不管有沒有
合併、合併幾輪，所有測試裡 P17 都正確排名第一、跟第二名差距至少
30 個百分點以上——**信心分數本身會波動，但「排名結果」始終穩定正確**，
實務上比較該看的是有沒有正確排第一、差距夠不夠大，不用糾結分數本身
的小數點差異。

## 快速測試

```bash
cd backend

# 用現成的偵測結果 json（離線，不呼叫任何模型）
python locate_photo_v2.py \
    --map output/topomaps/資工系系辦/topomap.json \
    --detections output/sessions/<id>/annotated/detections_<n>.json \
    --photo output/sessions/<id>/photo/<n>.jpg \
    --top-k 5 \
    --json-out locate_queries/result.json \
    --debug-png locate_queries/debug.png

# 或讓 CLI 自己跑一次偵測（預設 VLM 模式，需要 VLM_BACKEND 對應的 API 金鑰）
python locate_photo_v2.py \
    --map output/topomaps/資工系系辦/topomap.json \
    --photo /path/to/new_photo.jpg \
    --detect-mode vlm \
    --goal "尋找電腦"   # 可選，VLM 模式才會用到

# VLM 模式每次觀察細節不完全一樣，想降低信心分數波動可以跑多輪合併
# （實測下來 --detect-runs 2 波動縮小最明顯，見下方「多輪偵測合併」）
python locate_photo_v2.py \
    --map output/topomaps/資工系系辦/topomap.json \
    --photo /path/to/new_photo.jpg \
    --detect-runs 2
```

`--detections` 格式跟 `output/sessions/<id>/annotated/detections_*.json`
完全相同（`{"detections": [...], "ocr": [...]}`）。`--detect-mode` 還有
`groundingdino`（強制只用 GroundingDINO，失敗直接報錯）跟 `auto`（模擬
`server.py` 的行為：先試 GroundingDINO，失敗才退回 VLM）可選。

## 除錯用地圖圖片（`--debug-png`）

把查詢照片畫成地圖上的一個**獨立節點**（紅星標示），跟它配對到的物件
用細線連到對應的候選節點——但**不會**幫查詢節點接任何走道邊，接了不管
接在哪個候選節點後面，排版都會把它畫成「路徑接下去的某一步」，容易
誤導成「這是導航會走到的下一個地方」。所以查詢節點完全獨立於路徑之外
（`_dead_reckon_tree()` 找不到路徑的節點，會被擺到整張地圖版面外、留
足夠安全距離的空白區域，不會疊到主路徑或物件群上）。完全沒有改動
`TopoGraphV2.render_png()` 本身的繪圖邏輯。

## 這次疊代過程中找到並修正的問題

用真實資料反覆測試時，陸續發現並修好這些問題（大致按發現順序）：

| 問題 | 修正 |
|---|---|
| 覆蓋率公式對「查詢照片多看到不相干東西」不公平 | 改成雙向覆蓋率的調和平均 |
| 水平位置／左右關係會隨拍攝站位、朝向改變甚至鏡像顛倒 | 位置比對只看垂直，不看水平 |
| 垂直位置差一格被當成完全沒對上 | 差一格給部分加分，只有差兩格才不加分 |
| 物件很少的節點靠單一配對虛報高分 | 覆蓋率分母加平滑項（+1.2） |
| 只看物件種類，沒看排列順序合不合理 | 加入空間排列一致性檢查 |
| 「證據不足」跟「證據夠但沒差異可比」罰得一樣重 | 拆成兩種情況，分別給 0.5 / 0.85 |
| 標籤詞彙不統一（sofa/couch、cabinet/cabinet shelf） | 擴充 `LABEL_SYNONYMS`，比對取最長變體優先 |
| 除錯圖裡查詢節點被誤認成路徑的一部分 | 查詢節點完全獨立、不連走道邊 |
| 找不到路徑的節點排版跟主路徑重疊 | 擺到版面外、留足夠安全距離的空白區域 |
| **查詢偵測模式（GroundingDINO）跟地圖建圖模式（VLM）不一致** | CLI 新增 `--detect-mode`，預設改成 VLM，跟地圖用同一套方法 |
| **OCR 資料從建圖那一步就沒真正接到物件上**（`ocr_items` 參數接了但沒用） | 在建圖核心函式補上「OCR 關聯到最近物件」的邏輯，處理多物件共用同一個模板框時的平手判斷 |
| 帶 OCR 文字的結構物（例如貼牌子的門）被一律排除 | 沒有文字的結構物才排除，帶文字的破例放行 |
| VLM 模式偵測不穩定，每次觀察細節不完全一樣，信心分數波動大 | 新增 `--detect-runs N` 多輪偵測合併 |
| **多輪合併一開始用「標籤+精確位置」判斷是否同一物件，位置判斷有落差就誤拆分，物件數越合併越膨脹** | 改成「同標籤取單一輪次裡出現次數最多的那組」，不受位置判斷落差影響 |

## 用真實地圖資料驗證過的結果

**案例一**：desk/chair/sofa 高辨識度物件，早期版本只給 12.5%（覆蓋率
公式的問題），修正後回升到 56%。

**案例二**：P15 節點只有 3 個物件（2 門 + 1 個帶「會議室」牌子的
`sign`）。OCR 關聯修好前 24%（OCR 沒接上、配對數又太少）；修好後
`sign` 這組配對分數從 0.97 跳到 2.17，最終分數升到 50%（卡在「只配對到
1 組」的空間排列一致性懲罰，這是這張照片本身物件太少的合理上限，不是
公式問題）。

**案例三**：CGU AIR 平台恢復服務、拿到新 API 金鑰後，第一次真正用
`--detect-mode vlm --photo`（不給 `--detections`，讓 CLI 真的呼叫 VLM）
測試 P17，三次獨立呼叫分數落在 77.7%~83.0%，每次都正確排名第一、跟
第二名（P1，38~41%）差距超過 40 個百分點——證實「查詢照片改用 VLM
偵測、跟地圖用同一套方法」這件事，確實解決了原本「同一張照片測試卻
信心度過低」的核心問題。多輪合併（`--detect-runs`）驗證結果見上方
「多輪偵測合併」章節。

## 還沒做的部分

- 沒有利用「使用者剛剛在哪個節點」這種時序資訊縮小搜尋範圍——目前是對
  整張地圖的所有真實節點做全比對。`localize_photo()` 本身沒有限制候選
  節點清單，之後想加的話可以在呼叫端先用 `current_position` /
  `position_history` 篩選過再傳進去。
- 沒有視覺特徵向量，純規則式比對（標籤 + OCR + 垂直位置 + 排列順序），
  兩個標籤相同但其實是不同實體的東西（例如地圖上兩間都有的「白板」），
  只靠標籤還是分不出來，這是規則式方法的天花板。
- 目前只回答「最可能是哪個節點」，還沒有「接近哪個節點」或「介於哪兩個
  節點之間」這種模糊呈現方式——地圖的走道邊也沒有實際距離資料
  （`distance_m` 幾乎都是 `None`），要做「介於中間多少比例」這種有精確度
  的說法之前，得先讓建圖流程真的填入距離，不然呈現出來的數字只是編出來
  的假精確。
- **既有地圖需要用修正後的 `topomap_v2.py` 重新跑 `build_topomap_v2.py`
  （加 `--fresh`）才能吃到 OCR 關聯、標籤同義詞這些修正**——這些修正
  只影響「以後建圖/定位時」的行為，不會回頭修改已經建好的地圖資料。
- `--detect-mode vlm`（以及多輪合併 `--detect-runs`）已經用真實 API
  金鑰驗證過能正常運作，見上方「用真實地圖資料驗證過的結果」案例三；
  `--detect-mode groundingdino`/`auto` 這兩條路徑目前還沒有實測過
  （沙盒環境沒有裝 GroundingDINO 相關套件與模型權重）。
- 多輪合併目前只用「單一輪次裡出現次數最多」判斷同標籤該算幾個，沒有
  更精細地利用「跨輪次的畫面位置」資訊去互相佐證同一個實體——這是
  刻意的取捨（避免重蹈位置判斷落差造成誤拆分的覆轍），如果之後想做
  更精準的跨輪次物件對應，需要更穩健的空間匹配方式，不能只靠字串
  比對位置文字。
