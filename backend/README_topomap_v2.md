## 檔案清單（放到專案對應路徑即可）

```
backend/server/topomap_v2.py          核心資料結構（兩種節點、四種邊、子圖）
backend/build_topomap_v2.py           CLI：讀 output/sessions/<id>/ 生成地圖
backend/tests_fixtures/make_sample_session.py   沒有真實資料時的假資料產生器
backend/server/tests/test_topomap_v2.py         單元測試（16 個，全過）
```

`topomap_v2.py` 完全獨立於現有的 `topomap.py`，不會動到你系統原本的邏輯，
`session.py` / `server.py` 目前都沒有被修改。

## 快速測試（不需要真實導航資料）

```bash
cd backend
python tests_fixtures/make_sample_session.py --out /tmp/demo_session
python build_topomap_v2.py --input /tmp/demo_session --place "測試賣場 demo店"
```

會輸出：
- `output/topomaps/測試賣場_demo店/topomap.png` — 完整版（物件＋所有邊）
- `output/topomaps/測試賣場_demo店/topomap_overview.png` — **總覽版**（只有照片節點
  ＋走道邊，先看這張比較容易看懂整體路線走向）
- `/tmp/demo_session/topomap_v2/` 底下也會各存一份，方便對照這次導航的輸出

再跑一次同一個 `--place`（用新的 session 資料夾）就可以看到它會接在舊地圖後面，
而不是從頭重建。

## 用真實資料測試

你系統現在每次導航會把資料存在 `output/sessions/<session_id>/`，裡面已經有
`photo/`、`annotated/detections_*.json`、`map/map_*.json`，格式跟這支腳本預期的
完全一樣，所以可以直接：

```bash
python build_topomap_v2.py --input output/sessions/<session_id> --place "資工系系辦"
```

## 資料結構對照筆記

| 筆記中的概念 | 對應實作 |
|---|---|
| 第一種節點（拍照位置） | `TopoGraphV2.add_photo_node()`，`ntype="photo"` |
| 第二種節點（辨識到的物件） | `add_object_node()`，`ntype="object"`，含 `role`（商品／標示牌／環境） |
| 子圖 | `get_subgraph(photo_id)` |
| 第一種邊（photo→object，9 種子型態＋距離） | `add_contains_edge()` / `contains_etype()` / `grid_cell_from_box()`，`estimate_distance_m()` 是沒有手機感測器時的暫時公式 |
| 第二種邊（相鄰物件） | `add_adjacent_edge()`，依左到右排序後連相鄰兩兩物件 |
| 第三種邊（跨照片同物件） | `link_same_objects_between_photos()`，貪婪配對（標籤＋OCR招牌＋位置） |
| 第四種邊（走道，單向＝拍照方向） | `add_walkway_edge()`，路徑終點另外呼叫 `set_terminal_facing()` |
| 使用者目前位置 + 移動路徑 | `current_position` / `position_history` / `move_to()` |
| 虛假照片節點（沒走的路） | `add_virtual_branch()` / `resolve_virtual_branch()` |
| 依場所持久化、跨導航更新 | `save_for_place()` / `load_for_place()` |

## 還沒解決 / 只做了局部方案的部分（筆記裡列出的問題）

- **區域呈現**：目前只是在照片節點加一個 `region` 欄位當標籤，不是真正的區域子圖。
- **前後照片沒有共同物體**：`link_same_objects_between_photos()` 配對數是 0 時不會報錯，
  但也沒有補救機制，呼叫端要自己注意。
- **貨架物體被視為整體**：這個要等你們實際用 GroundingDINO 跑過賣場資料才能評估，
  目前的物件節點結構本身沒有限制，但關聯/角色判斷的準確度會受影響。
- **使用者走出已建地圖範圍**：`move_to()` 目前預設要求兩個照片節點間必須已經有
  走道邊才能移動（`require_walkway=True`），走出範圍時會丟出例外，還沒設計自動處理方式。

物件關聯（第三種邊）跟角色判斷都是先用「標籤/OCR文字比對」的規則式做法，
沒有像 ConceptGraphs 那樣用 CLIP 語意相似度，因為目前系統的偵測結果本來就沒有
視覺特徵向量。如果之後想比照論文做法，可以在 `link_same_objects_between_photos()`
裡加一個可選的 embedding 相似度分數。

物件相鄰關係文字（第二種邊）目前是模板產生（`"{A} 在 {B} 的左側"`），
`build_subgraph_from_detections()` 有留 `relation_fn` 參數，可以接你們的
`llm_gateway.py` 讓 LLM 生成更自然的描述，先沒串是因為想讓這支腳本能完全離線跑。

## 這次改了什麼（2026/07/19，根據你上傳的 8 節點真實資料調整）

**1. 地圖太亂 → 換掉版面配置**

原本用 `nx.spring_layout()`，節點位置是演算法自己「彈簧模擬」出來的，
節點一多就會擠成一團互相纏繞。改成沿著走道邊排成一直線的「主幹＋吊掛物件」
版面：照片節點照實際走的順序排一排，物件節點吊在自己照片節點下方，
一眼就能看出使用者實際走的路線。另外新增 `render_png(mode="backbone")`，
只畫照片節點跟走道邊，需要先看整體路線走向時可以先看這張。

**2. 跨照片同物件關聯過度連結 → 收緊判斷門檻**

你上傳的真實資料裡，8 張照片、74 個物件卻連出 72 條「同物件」邊，
仔細看內容發現大多是 `trash↔trash`、`desk↔desk`、`plant↔plant` 這種
被誤判的配對。原因是實際系統輸出的 `detections_*.json` 幾乎都沒有
`position` 欄位，導致我原本設計的評分公式退化成「標籤字串一樣就算配對」
——而辦公室走廊裡本來就到處都是垃圾桶、桌子、盆栽，光看標籤完全無法
區分是不是同一個。這次改成：
  - 沒有 `position` 欄位時，改用偵測框座標自己算一個畫面位置（左右／上下），
    不再依賴那個常常是空的欄位；
  - 配對門檻從 1.0 分提高到 1.6 分，代表「只有標籤一樣」不足以判定為同一物件，
    至少要多一項空間位置或招牌文字佐證；
  - 預設不對「門、牆、窗」這類環境／結構物件做跨照片關聯（`allow_structural=True`
    可以覆蓋），因為這類物件每張照片幾乎都會出現，用標籤配對幾乎一定會誤判。

## 這次又改了什麼（同一天，第二輪：配色、節點文字、目前位置標示）

- **節點改成「依文字內容自動算多大」的方塊**，不再是固定大小的圓點/方塊。
  文字絕對不會被截斷、也不會突出節點邊界；連 `cabinet bookshelf shelf` 這種
  很長的組合標籤都能完整顯示在自己的框裡。
- **節點間距也改成依方塊實際大小計算**，不再用固定間距，所以不會互相重疊
  （包括物件群跟隔壁照片的物件群）。
- **換了一組更柔和的配色**：照片節點深藍綠 `#264653`，物件節點暖金色
  `#E9C46A`，走道邊珊瑚橘、相鄰邊青綠、跨照片同物件邊紫色，比原本飽和的
  藍/橘更耐看。
- **圖例改成畫布最上方的獨立橫條**，不再疊在圖的左上角蓋住節點（圖比較小
  的時候原本會蓋到）。
- **「使用者目前位置」從蓋住整個節點的巨大紅色星星，改成畫在該照片節點
  右上角的一顆小紅星徽章**——見下方說明。

### 那顆紅色大星星是什麼意思？

代表**使用者目前所在的照片節點**（也就是 `current_position`，導航到目前
為止最後拍到的那個位置）。舊版是畫在節點正中央、蓋住文字的巨大星星；
新版改成畫在那個節點方塊右上角的小星星徽章，一樣代表「這裡是目前位置」，
但不會擋住節點本身的標籤。

## 這次改了什麼（第三輪：死算推位版面，貼近實際場景分布）

之前的版面是把所有照片節點強制排成一條直線（不管實際路線有沒有轉彎），
物件群固定吊掛在正下方。這次改成：

- **以第一張照片（id 最小）當原點 `(0, 0)`**，之後每個節點的位置都是從
  這裡沿走道邊「走」出來的——符合你說的「先把第一張照片定為原點」。
- **沿走道邊的方向文字做死算推位**：解析每條走道邊 `direction` 欄位裡的
  文字（這是 VLM 生成的自然語言，例如「請直走，然後再拍一張照片」「請
  右轉」），抓「左轉／右轉／迴轉」等關鍵字轉換成角度，抓得到「幾公尺」
  的數字就用來抓步伐長度，抓不到就用一個固定的預設步長代替。這樣路線
  轉彎的地方，地圖上也會跟著轉，不再是死板的一直線。
- **物件群吊掛的方向會跟著走道朝向旋轉**：不再永遠掛在正下方，而是掛在
  該節點所在那段走道的側邊，路線轉彎時，物件群的方向也會跟著轉，比較
  像貼著實際走道排列。
- **虛假分支節點（沒走過的路）也會依方向文字偏到正確的側邊**（例如
  「往右側走道」就會偏到主線的右側，不是疊在主線正上方）。
- 節點間距、防止文字重疊的邏輯不變，只是現在整體形狀是 2D 的，不是一維的。

**這仍然只是「大概的形狀」，不是量出來的真座標**——沒有羅盤/步伐感測器，
角度只能抓文字裡的關鍵字（例如「先直走再右轉」這種同一句話裡出現多個
動作的複雜語句可能抓不準），距離抓不到數字時也只能用固定步長代替。等
之後手機端真的送方向/距離感測器資料進來，可以把這裡的關鍵字解析換成
真正的感測器數值，形狀會更準確。

你上傳的這份真實資料裡，VLM 產生的方向文字全部都是「請直走／請繼續直走」
（沒有出現轉彎），所以死算推位算出來的形狀本來就會是一直線——這其實是
正確反映了這次真實路線本身就是一路直走。已經另外用合成測試資料驗證過
轉彎（直走→右轉→直走→左轉）會正確畫出轉折的形狀，附件裡也有這張測試圖。




## 這次改了什麼（第四輪：修掉節點互相覆蓋、放大文字）

你上傳的最新測試結果裡，物件節點會一整排疊在一起（例如
`cabinet bookshelf shelf` 疊在 `desktop computer water dispenser` 上面）。
原因找到了：物件群分成好幾「列」吊掛在照片節點側邊時，列與列之間的間距
原本用一個固定值（不管方塊多寬多高），但這次的路線（在你的真實資料裡）
剛好是正南北走向，導致「列跟列之間該留多少距離」跟「方塊本身的寬度」
變成同一個方向——方塊本身動辄 3~4 個資料座標單位寬，固定間距完全不夠，
所以整排疊在一起。

修法：現在會先算「方塊的寬/高投影到列間距方向後各佔多少空間」（矩形投影
到任意方向的公式：`|寬 × 該方向的水平分量| + |高 × 該方向的垂直分量|`），
再用這個真正需要的空間來決定列與列的間距，不管走道朝向是水平、垂直、還是
斜的，物件方塊都不會疊到彼此。

另外把照片節點跟物件節點的文字都調大了（照片節點 11pt → 13.5pt，
物件節點 9pt → 11pt），方塊大小是「先量文字多大再決定」，所以字變大、
方塊也會跟著變大，不會被截斷。

新增一個回歸測試 `test_object_rows_do_not_overlap_when_corridor_is_axis_aligned`，
用一堆長標籤 + 走道方向固定為正南北向（最容易踩到這個 bug 的情境）驗證
所有物件方塊兩兩之間都不重疊。

## 這次改了什麼（第五輪：修正「請轉身」沒被辨識成迴轉的 bug）

分析你這次上傳的真實 17 節點資料時發現：路線中段有「請向右轉」（有正確
辨識成右轉）跟兩次連續的「請轉身，然後沿著走廊返回」——但「轉身」這個
詞不在我原本的迴轉關鍵字清單裡（原本只有「迴轉」「掉頭」「回頭」），
導致這兩次迴轉被當成「沒有轉彎」處理，路線本來應該要折返，卻被畫成
繼續往同一個方向直走，跟真實走法對不起來。

修法：把迴轉關鍵字擴充成「迴轉、回轉、掉頭、回頭、轉身、折返、往回走、
退回」，涵蓋更多常見的翻譯講法。用你的真實資料重新驗證過：兩次連續的
「轉身」現在會正確疊加成 360 度（等於繞回原本方向），路線形狀也確實出現
折返效果，不再是一路直走的假象。

另外把節點文字原本設定的「粗體」拿掉了——這是造成你截圖裡那些
`findfont: Failed to find font weight...` 警告的原因（你的機器上找到的
中文字型檔案，matplotlib 沒辦法正確抓到粗體版本，抓不到就退回很細的字重，
警告訊息不影響地圖產生，但看起來很吵）。文字現在維持一般字重，配合已經
放大的字級，還是清楚易讀。

新增 2 個測試：`test_parse_turn_degrees_recognizes_turn_around_phrasing`
（驗證「請轉身」「請往回走」「請掉頭」都能正確辨識成迴轉）、
`test_double_turn_around_cancels_out_like_real_session_data`（直接對應
你這份真實資料連續兩次迴轉的情境，驗證角度真的有疊加抵銷回原方向）。

## 這次改了什麼（第六輪：同物件關聯邊變兩條弧線、P0/P8/P15 是什麼意思）

**Q: 判定為同物件的兩個物件節點之間，為什麼畫出來是兩條弧線？**

因為第三種邊（跨照片同物件）在資料裡是「雙向各存一條」（`A→B` 跟
`B→A` 各一條，方便沿著任一方向查詢鄰居），這是設計上故意的，不是錯誤。
但畫圖時如果把這兩條方向相反的邊都畫出來，因為用的是有弧度的線
（`connectionstyle="arc3"`），方向相反時弧會往兩邊彎，疊在一起就變成
你截圖裡看到的「兩條弧線像一對眼睛」。

**這是純粹的畫圖問題，資料本身沒有錯**——但既然會造成誤解，還是修掉了：
畫圖前先把每一種雙向邊（相鄰物件、跨照片同物件、走道）都依「無序的節點
對」去重，同一對節點只畫一條線／一條弧。用你的真實資料重新產生過，
原本的雙弧線現在只剩一條。

**Q: 照片節點的 P0、P8、P15 是什麼意思？**

這是圖裡「內部節點編號」——整張圖不管是照片節點還是物件節點，全部共用
同一個流水號，每張照片底下通常會接著建立好幾個物件節點，所以下一張照片
的編號常常會跳號（例如 P0 後面接了 7 個物件節點，下一張照片就變成 P8）。
這個號碼本身沒有「第幾張照片」的意思，只是建立順序的內部參考編號，
容易讓人誤會。

已經改成畫圖用的標籤直接顯示「這是第幾張照片」（P1＝第一張、P2＝第二張…），
不再顯示內部編號，之後每張照片幾號應該就會很直覺了。

新增 2 個測試：`test_photo_label_uses_sequence_number_not_internal_id`
（驗證標籤真的是第幾張照片，不是內部 id）、
`test_same_object_edge_only_drawn_once_not_twice`（驗證雙向邊去重後
只剩一條）。

## 這次改了什麼（第七輪：路線折返時，全域防止蓋到其他節點）

之前的防重疊只保證「父節點→子節點」這種直接相鄰的關係不會疊到。但路線
折返（例如右轉、直走、然後連續兩次「請轉身返回」）時，折返點會跟很久
以前經過、但在樹狀結構上不相鄰的節點，在空間座標上剛好靠在一起——這種
情況沒有被檢查到，折返點的物件群就可能蓋到別的節點。

修法：新增一輪全域防重疊後處理（`_resolve_cluster_overlaps`）。把每個
照片節點跟它自己的物件群當成一個整體（一起移動，不會打亂群內部的排列

### 1. 物件節點的九宮格排列順時針轉 90 度，九宮格上方對齊圖片上方

第十一輪把排列改成「固定三欄、欄內往外堆疊」解決了排成一直線的問題，
但欄跟堆疊套用的軸剛好對調了：欄（左/中/右）沿著「走道前進方向」
展開、堆疊（上/中/下）沿著「走道側邊」展開——實際畫出來，欄變成
上下排、堆疊變成左右排，跟「左右對應畫面左右、上下對應由近到遠」
的直覺是反的。

修法：把兩個軸對調，等於整個排列繞照片節點順時針轉 90 度——
**欄（左/中/右）改成沿走道側邊展開**（現在才是左右排），**同一欄內
由近到遠的堆疊改成沿「背對前進方向」展開**（現在才是上下排，而且
背對前進方向，不會往下一個照片節點延伸過去）。九宮格的「上/中/下」
本來是決定堆疊順序，這點不變，只是換了方向：上排物件還是堆最靠近
照片節點，下排堆最遠，只是現在這個「近→遠」呈現在畫面的「上下」
關係，而不是「左右」關係。

順便修正了一個沒有回報但這次一起發現的小瑕疵：欄與欄之間需要留多少
間距，原本直接用物件文字方塊的「原始寬度」（沒有考慮走道朝向），
走道是斜角時這個估計會不準；這次改成跟堆疊間距一樣，用矩形投影到
實際欄位展開方向後的寬度來算，轉彎、斜角的路線也會準確。

兩個既有的排版方向測試（`test_object_layout_follows_grid_cell_column_order`
／`test_object_layout_follows_grid_cell_row_order`）跟著改了投影用的軸
（欄的測試改投影到 perp_axis、堆疊的測試改投影到 `-row_axis`），語意
本身沒變（左還是要在中的負方向、右在正方向；上排還是要比中排、下排
更靠近照片節點），只是配合這次的 90 度旋轉更新對照的軸。

### 2. 箭頭不遮擋節點內容、節點間不重疊

這點沿用第十一輪已經做好的防護機制（`_resolve_cluster_overlaps` 防止
節點群整塊重疊、`_resolve_edge_node_crossings` 防止走道邊被無關節點
擋住），旋轉排列方向之後重新驗證：用你這份真實資料（17 張照片、
75 個物件）實際跑過，**節點兩兩重疊維持 0 對，跨群的走道邊穿越問題
維持 0 條**——確認轉 90 度這個改動沒有讓這兩個問題重新出現。

單元測試都更新後全部通過，總數維持 43 個。
